## 【发现的Schema冲突】

**DBI 报告 CONFIRMED**（三层证据）：

1. **文档层**：`docs/DATABASE_SCHEMA.md` v2 = items 逻辑删除（deleted_at）、item_records FK RESTRICT、DELETE=UPDATE、查询过滤 `deleted_at IS NULL`；`docs/API_CONTRACT.md` v2.2 §3.9/A16 仍为硬删除级联（DATABASE_SCHEMA §11 已注明"API_CONTRACT §3.9/A16 与 TASKS 验收项待总控同步"，SCHEMA_CHANGE_PROPOSAL-001 待批）。
2. **代码层**：migration（`1787132713236-CreateTables.ts`）与 `item.entity.ts`/`item-record.entity.ts` 已是 v2 口径；但 `items.service.ts:133-137` `remove()` 仍 `items.remove(item)` 物理删除，注释仍写"契约 3.9：硬删除"；且 list/getById/findOwned 均无 `deleted_at IS NULL` 过滤（v2 要求全查询显式过滤，DATABASE_SCHEMA §9.7）。
3. **测试层（实证）**：`test/main-chain.e2e-spec.ts:431-453` 仍按硬删除断言（204 + records/images 清零）。现场跑 e2e：
   - `QueryFailedError: update or delete on table "items" violates foreign key constraint "FK_cff4e76e0e1bb5d110a6c8244bc" on table "item_records"` → 500（期望 204）。
   - 即：**删除带记录的玩物 = 500**；删除无记录玩物 = 物理行消失（违反"保留可恢复"）。

## 【发现的API冲突】

1. **[阻断级] 删除语义三段漂移**（如上）：API_CONTRACT §3.9/A16（硬删级联）vs DATABASE_SCHEMA v2（逻辑删除）vs 代码（migration 已 v2、service 仍硬删）。建议总控先批准 SCHEMA_CHANGE_PROPOSAL-001 并同步 API_CONTRACT §3.9/A16 与 TASKS M1-003 验收⑤，再派发 M1-003 整改，避免 BE 二次返工。
2. **[记录级] `POST /v1/uploads` 受全局鉴权**（uploads.controller 无 `@Public()`）：契约 §3.10 未明文要求鉴权；e2e 已按"需 token"断言（noAuth→401）。M1 主链无影响（iOS 上传均在登录后），建议总控在契约 §3.10 补一句"需登录"或在裁决记录备案。
3. **[记录级] 上传扩展名白名单含 `heif`**（契约列 jpeg/png/heic/webp）：代码注释说明 iPhone 实拍可能输出 .heif，属合理实现；建议契约同步补录 heif。
4. **[记录级] 畸形 JSON 请求体**：返回 `VALIDATION_ERROR` 但 message 为英文原始解析信息（非中文可读），不泄漏路径/栈，不阻断。
5. TASKS M1-003 验收⑤（"DELETE 204 且 DB 层级联删除 records/images"）与 M1-005 相关表述为 v2.2 旧口径，随契约同步更新。
